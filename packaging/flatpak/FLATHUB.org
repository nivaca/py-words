#+TITLE: Publishing py-words on Flathub
#+STARTUP: overview

* Overview
Flathub (https://flathub.org) builds Flatpaks from a manifest kept in its
own GitHub repository, one per application, and publishes them for every
Flatpak user (=flatpak install flathub io.github.nivaca.PyWords=).
- Application ID :: =io.github.nivaca.PyWords= (verified through the
  GitHub account nivaca: nothing to put on a web site)
- Manifest here :: =packaging/flatpak/io.github.nivaca.PyWords.yml=
- Metainfo :: =packaging/flatpak/io.github.nivaca.PyWords.metainfo.xml=,
  installed from the program's own sources, so it travels with each tag

The manifest here builds from the working tree (=tools/bundle-flatpak.py=
puts the files of the zip there).  Flathub builds from a git tag instead:
=tools/bundle-flatpak.py --flathub FOLDER= writes that manifest, for the
tag vVERSION (which must exist: =tools/release.py= makes it).

The first version to submit must be one whose tag has =packaging/flatpak/=
(3.15 or later): the build reads its metainfo and desktop files from there.

* Before submitting: check it here
** 1. Build and run it
#+begin_src sh
python3 tools/bundle-flatpak.py --install
flatpak run io.github.nivaca.PyWords
#+end_src

** 2. The linter Flathub runs
#+begin_src sh
flatpak install --user flathub org.flatpak.Builder
python3 tools/bundle-flatpak.py --flathub build/flathub
flatpak run --command=flatpak-builder-lint org.flatpak.Builder \
    manifest build/flathub/io.github.nivaca.PyWords.yml
flatpak run --command=flatpak-builder-lint org.flatpak.Builder \
    repo build/flatpak/repo
#+end_src
The x11 socket is on purpose (Tk has no Wayland), and so is the network
(the browser reaches the page of =py-words web=); if the linter or the
reviewers ask, that is the answer.

* Submitting (once)
Flathub's own guide: https://docs.flathub.org/docs/for-app-authors/submission
1. Fork https://github.com/flathub/flathub on GitHub, and in the fork make
   a branch from =new-pr= (not from =master=).
2. Put in it the manifest written by =--flathub= (only that file).
3. Open a pull request against =new-pr=, titled
   "Add io.github.nivaca.PyWords".  A test build runs on it
   (comment =bot, build= to run it again).
4. When it is merged, Flathub makes the repository
   https://github.com/flathub/io.github.nivaca.PyWords, with you as a
   maintainer (accept the invitation), and publishes the app.

* Each new version
1. In the metainfo, a new =<release>= at the top (the bump checklist in
   =version.py= says so, and =tests/test_bundle_flatpak.py= checks it).
2. After =tools/release.py= has pushed the tag, Flathub's external data
   checker (=x-checker-data= in the generated manifest) notices it within
   hours and opens a pull request in flathub/io.github.nivaca.PyWords with
   the new tag and commit; merge it when its test build passes.
   By hand instead: =tools/bundle-flatpak.py --flathub= in a clone of
   that repository, and a pull request.
3. A new Tcl/Tk 9.0.x or a new runtime: the checker proposes the Tcl/Tk
   ones too; a runtime change (=runtime-version=) is made here first and
   must keep its Python's version the same as the one of the CPython
   sources of the tkinter module.
